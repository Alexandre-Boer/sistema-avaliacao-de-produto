# Sign-In (Autenticação) — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permitir que uma pessoa entre na plataforma com e-mail e senha: página `/auth/sign-in`, endpoint `POST /api/v1/sign-in` que valida credenciais contra `accounts` e abre uma sessão por cookie, e cabeçalho que mostra "Entrar" ou o avatar com nome, sobrenome e e-mail.

**Architecture:** Mesmo padrão do sign-up: schema zod compartilhado entre formulário (react-hook-form) e Route Handler; serviço `authenticate` lê a conta via client service-role e compara a senha com `bcrypt.compare`; sucesso emite um JWT assinado (módulo `src/lib/session.ts`, pronto na Fase 0) enviado como cookie `HttpOnly`. O cabeçalho é um Server Component que lê `getSession()` dentro de `<Suspense>` (obrigatório com `cacheComponents`) e renderiza o botão de login ou o menu do usuário (avatar DiceBear + "Sair").

**Tech Stack:** Next.js 16 (App Router, `cacheComponents`), React 19, react-hook-form + zod, TanStack Query, bcryptjs, jose, shadcn/ui (`avatar`, `dropdown-menu` já instalados), Vitest + Testing Library.

**Spec:** `docs/specs/sign-in.md` (ver também `docs/plans/2026-11-13-orquestracao.md` para contratos e donos de arquivos)

## Global Constraints

- Endpoint `POST /api/v1/sign-in`, JSON no body; `200` sucesso (cria sessão por cookie); `400` má formatação; `401` falha de credenciais.
- Erro de autenticação sempre genérico: **"E-mail ou senha inválidos"** (nunca dizer qual campo falhou).
- Credenciais lidas da tabela `accounts` (colunas `email`, `password` = hash bcrypt, `active`).
- Página em `/auth/sign-in`, formulário com validação no cliente, erro em alert vermelho, sucesso navega para `/`.
- Cabeçalho: deslogado → botão "Entrar"; logado → avatar (DiceBear) com nome + sobrenome e e-mail.
- Arquivos de outros donos (ver orquestração) **não** são editados; em especial `src/lib/session.ts`, `src/lib/validation/sign-up.ts`, `package.json`, `components/ui/**`.
- Lint/format com Biome; TypeScript estrito; Server Components que leem `cookies()` ficam dentro de `<Suspense>`.
- Desvio consciente: `POST /api/v1/sign-out` (não está na spec; necessário para sair da conta). Registrar no `Resultado`.

## Review Focus

1. **E-mail inexistente vs. senha errada** devem produzir a mesma resposta (`401`, mesma mensagem) e tempo semelhante: o serviço compara contra um hash dummy quando a conta não existe. Testes: Task 3 (passos 1: "conta inexistente" e "senha incorreta" ambos lançam `InvalidCredentialsError`; e "chama compare mesmo sem conta").
2. **Conta inativa (`active = false`)** não pode entrar. Teste: Task 3 (passo 1, caso inativo).
3. **E-mail com maiúsculas/espaços** deve achar a conta normalizada pelo sign-up. Teste: Task 1 (normalização).
4. **Cookie sem flags de segurança** expõe a sessão: `HttpOnly`, `SameSite=Lax`, `Path=/`. Teste: Task 4 (passo 1, header `set-cookie`).
5. **Header não atualiza após login** (Server Component cacheado): o formulário chama `router.refresh()` além de `router.push("/")`. Teste: Task 5 (passo 1, caso sucesso verifica `refresh`).
