# Sign-Up (Criação de conta) — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Criar a base do projeto Next.js e o fluxo completo de criação de conta: página `/auth/sign-up` com formulário validado, endpoint `POST /api/v1/sign-up` e persistência na tabela `accounts` do Supabase.

**Architecture:** Monolito Next.js (App Router, pasta `src/`) servindo UI e API. O endpoint de sign-up é um Route Handler REST em `/api/v1/sign-up` (a spec fixa o path e os status codes HTTP, o que é incompatível com o envelope do tRPC — a configuração do tRPC fica adiada para a primeira feature que o utilize). A lógica de negócio vive em um serviço (`createAccount`) compartilhável, que usa um client Supabase server-side (service role) e bcryptjs para hash de senha. O schema de validação (zod) é compartilhado entre cliente (React-Hook-Form) e servidor.

**Tech Stack:** TypeScript, Next.js, React, TailwindCSS, shadcn/ui, React-Hook-Form + zod (`@hookform/resolvers`), TanStack React Query, bcryptjs, nanoid, `@supabase/supabase-js` (Postgres no Supabase), Biome, Vitest + Testing Library.

**Spec:** `specs/sign-up.md` (complementada por `docs/ARCHITECTURE.md`)

## Global Constraints

- Endpoint: `POST /api/v1/sign-up`, dados em JSON no `body`; sucesso retorna `201`; má formatação de dados retorna `400` (valores fixados pela spec).
- Tabela `accounts` com as colunas da spec: `id` (nanoid gerado na camada de API), `first_name`, `last_name`, `created_at`, `updated_at`, `active`, `email`, `password` (hash), `salt`.
- Página do formulário em `/auth/sign-up`; sucesso navega para `/auth/sign-up/success`; erros aparecem em um alert vermelho no formulário.
- Hash de senha com **bcryptjs** (decisão registrada em `docs/ARCHITECTURE.md`, substituindo o Crypto nativo). O salt gerado é armazenado na coluna `salt` para cumprir a spec, ainda que o bcrypt o embuta no próprio hash.
- Escopo restrito a sign-up: nenhum envio de e-mail, nenhuma outra funcionalidade (sem login, sem recuperação de senha).
- Lint/format com Biome; TypeScript em modo estrito.
- Desvios conscientes da spec (documentar no `Resultado` ao final): `timestamptz` em vez de `timestamp` (boas práticas Postgres); e-mail duplicado retorna `409` (a spec só define 400 para má formatação e não trata duplicidade — 500 seria inaceitável).

## Review Focus

1. **E-mail já cadastrado** → `POST` repetido com o mesmo e-mail deve retornar `409` com mensagem clara no formulário, nunca `500`. Testes: Task 5 (passo 1, caso `23505`) e Task 6 (passo 1, caso 409).
2. **Body não-JSON ou JSON inválido** → requisição com body corrompido deve retornar `400`, não derrubar o handler. Teste: Task 6 (passo 1, caso body inválido).
3. **Bypass do cliente com senhas divergentes** → chamada direta à API com `password ≠ passwordConfirmation` deve falhar com `400` (validação servidor). Testes: Task 3 (passo 1, caso mismatch) e Task 6 (passo 1, caso 400 de schema).
4. **E-mail com maiúsculas/espaços** → `" Ana@X.com "` deve ser normalizado (trim + lowercase) antes de validar/salvar, evitando duplicatas lógicas na coluna única. Teste: Task 3 (passo 1, caso normalização).
5. **Senha fraca/curta** → senha com menos de 8 caracteres deve ser rejeitada nas duas camadas (o schema é compartilhado). Testes: Task 3 (passo 1, caso senha curta) e Task 7 (passo 6, erro exibido no formulário).
